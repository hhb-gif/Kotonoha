> 记录时间：2026-08-19

## 目标

跑通最小闭环：视觉小说风前端壳 + dsh 真实 agent 后端。

- 对话：模型与用户交替（真实 LLM 驱动）

- 单模型单角色，架构预留多模型多角色（不同模型 = 不同角色）

# 阶段二：游戏化 Agent 入口 + App 化（规划）

> 记录时间：2026-08-20
> 状态：🔄 执行中（第一轮：故事/存档/主界面/ESC/Electron；第二轮：UI 重构四反馈——主界面美化、项目点选制、ESC 页签化、历史日志；详见 `docs/records/2026-08-20-phase2-round1.md` + `phase2-round2.md`）
> 待办：Electron 重新打包（UI 重构后产物过期）、审批裁决真实调用实测

## 目标

把 Kotonoha 从「单存档视觉小说壳」升级为「游戏式 Agent 应用」：

1. **日志层** —— 对话中可查看完整历史记录（不透明叠加层）
2. **故事/存档体系 + 主界面重建** —— 故事 = 工作区，存档 = 对话记录，每故事独立存档体系；游戏入口式主界面 + 左右分割选择界面
3. **ESC 面板** —— 对话中按 ESC 打开角色面板：存档配置信息 + Agent 技能（道具/技能包装）调控
4. **打包 App** —— Electron 封装为可下载、独立 UI 的桌面应用

## 一、日志层

| 项 | 设计 |
|---|---|
| 入口 | 对话界面顶栏「日志」按钮 + 快捷键 `L` |
| 呈现 | 全屏不透明深色叠加层（视觉小说回顾风），居中单列滚动：每条消息 = 角色名 + 完整文本（沿用 cleanMarkdown 后文本） |
| 交互 | 滚轮滚动；ESC / 点击背景 / 关闭按钮退出 |
| 数据 | 直接读 App 的 `messages`（无需额外存储）；当前展示进度（shownIndex/pageIndex）不受影响 |

## 二、故事 / 存档体系 + 主界面

### 数据模型（localStorage）

```
kotonoha:stories         # 故事索引（全局）
  { stories: [{ id, name, path, createdAt }] }

kotonoha:saves:<storyId> # 每个故事独立的存档体系
  { saves: [{ id, name, sessionId, savedAt, lastActiveAt, preview }] }

kotonoha:context         # 当前上下文
  { storyId, saveId }
```

- **故事 = 工作区**：新建会话时 `session.create { cwd: story.path }`（对应现有 BASE_CWD 改造）
- **存档 = 会话记录**：sessionId + 元信息（名称/时间/预览），按故事隔离
- 现有单存档位 `SAVE_KEY` 迁移为多故事多存档

### 界面流

```
启动 → 主界面（游戏入口：标题 + 新游戏 / 载入 / 设置）
        ├─ 新游戏 → 选择界面（可新建故事/新建存档）→ 对话界面
        ├─ 载入   → 选择界面（仅已有故事/存档）→ 对话界面
        └─ 设置   → 现有设置面板
对话界面 → 顶栏「返回主界面」→ 主界面
```

- **选择界面**（新游戏/载入共用）：左右分割列 —— 左侧故事列表（含「新建故事」卡片：名称+路径输入）；选中故事后右侧显示其存档列表（新游戏模式含「新建存档」卡片；载入模式只选已有）；底部「进入」
- 对话界面顶栏「存档」改为「保存到当前存档 / 另存为新存档」；恢复主界面后再次进入直接回到上次上下文（可跳过选择）
- 风格延续：微软雅黑、紫黑配色、字体体系不变

## 三、ESC 面板（角色/存档/技能）

| 分区 | 内容 |
|---|---|
| 存档信息 | 故事名/路径、存档名、最后活动时间、消息数 |
| 模型配置 | 当前模型、密钥状态、文本速度、场景（汇总展示，可跳转设置） |

## 六、风险与对策

| 风险 | 对策 |
|---|---|
| localStorage 容量（历史重放走 dsh history，存档只存 sessionId） | 无容量压力；预览字段截断 80 字 |
| Electron 下 WS/HTTP 直连 3080 跨域 | main 进程代理或 webSecurity 白名单 |
| story.path 无效（cwd 不存在） | dsh session.create 失败 → 错误提示 + 返回选择界面 |
| 旧单存档数据兼容 | 启动迁移：SAVE_KEY → 默认故事「Kotonoha」下存档 |
| 技能开关真调控依赖 prompt 注入，模型可能不遵守 | 明确标注为「软调控」，后续可升级为 dsh 级过滤 |

## 六·补：技能硬调控探测结论（2026-08-20，`docs/records/approval-probe-2026-08-20.md`）

- **审批拦截可行（实测）**：新会话默认 `workspace-write` + `approval: ask`；越界工具调用（沙箱升级）会收到 `method:"approval/requested"` 帧（含 approvalId/toolName/callId/reason + 服务端签发 rpcId）；`POST /api/respond` 回显 rpcId + `outcome:"rejected"` → 工具真实不执行、`approval/decided(rejected)` 落日志、模型按指引收场、`turn/end completed`。
- **硬限制**：沙箱内合法调用零审批（工作区内 write 直接执行，无外部 hook）；审批只按「沙箱升级」触发，不按工具名；已存在会话的权限旋钮外部不可改（仅 settings 影响新会话）。
- **技能开关实现方案**：开关 = 「越界操作的自动审批决策器」—— 工具需要审批时，若该技能开关关闭 → 自动 `respond rejected`（硬拒绝）；开启 → 自动 `allow`。工作区内操作始终放行（标注为 dsh 硬限制）。另提供「严格模式」：新建会话时写入更严的 permission defaultPreset（settings.update），实现会话级硬调控。
- **风险**：审批帧无超时、mux 重连会重放挂起审批 → 桥接层兜底（超时自动拒绝 / session.cancel）。
